# 功能规格说明：平台基础设施（Platform Base）

**功能分支**: `001-platform-base`
**创建日期**: 2026-04-27
**状态**: Draft
**输入**: 合并自 inputs-base、checkpoints、flushers、normalization、core 五个原始模块

## 模块概览

本规格覆盖 LoongSuite Pilot 平台的全部基础设施，包括：

| 子模块 | 目录 | 职责 |
|--------|------|------|
| **输入源框架** | `src/inputs/base/` | 5 种采集基类，封装轮询、增量读取和状态管理 |
| **持久化层** | `src/checkpoints/` | StateStore（采集进度）+ SnapshotStore（IDE 去重） |
| **归一化层** | `src/normalization/` | 异构数据 → `AgentActivityEntry` → `SerializedLogEntry` |
| **数据输出** | `src/flushers/` | JSONL 本地文件、阿里云 SLS、HTTP POST + 多目标扇出 |
| **核心编排** | `src/core/` | 配置加载、Agent 发现、准入控制、输入管理、优雅关闭 |

## 用户场景与测试 *(必填)*

### 用户故事 1 — 插件式采集框架（输入源基类）（优先级：P1）

作为平台开发者，我需要一套可复用的采集基类，封装轮询循环、增量读取、状态持久化和事件发射等通用逻辑，使接入新 Agent 时只需继承基类并实现少量抽象方法。

**优先级理由**: 采集框架是所有 Agent 输入源的运行基础，没有它任何具体 Agent 都无法工作。

**独立测试**: 可通过创建一个最小化的 `BaseSessionInput` 子类，验证它能正确执行轮询、发射事件并持久化偏移量。

**验收场景**:

1. **Given** 平台提供了 5 种采集基类（IDE 快照、SQLite、Hook JSONL、CLI 转发、会话文件），**When** 开发者需要接入一个产出 JSONL 会话文件的新 Agent，**Then** 仅需继承 `BaseSessionInput` 并实现 `discoverSessionFiles()` 和 `processSessionLine()` 两个方法
2. **Given** 一个输入源已启动，**When** 轮询周期触发且 `collect()` 返回非空数组，**Then** 基类自动 emit `'entries'` 事件并调用 `stateStore.save()`
3. **Given** `collect()` 抛出异常，**When** 轮询继续，**Then** 错误被记录但不中断后续轮询周期
4. **Given** 一个输入源的数据文件中包含新增数据行，**When** 轮询周期触发，**Then** 系统仅读取自上次偏移量以来的新增数据（增量采集），不重复处理已采集的记录
5. **Given** 会话文件在进程停止期间被替换（inode 变化），**When** 进程重启，**Then** `BaseSessionInput` 检测到文件替换并从头开始读取新文件

### 用户故事 2 — 采集进度持久化与断点续采（Checkpoints）（优先级：P1）

作为平台运维人员，我需要系统在进程重启后能够从上次中断的位置继续采集数据，既不丢失未处理的记录，也不重复处理已完成的记录。

**优先级理由**: 断点续采是数据采集平台最基本的可靠性保障。

**独立测试**: 可通过设置某个输入源的偏移量为特定值并持久化到文件，重新加载后验证偏移量与保存时一致。

**验收场景**:

1. **Given** 一个输入源已处理数据到偏移量 1024，**When** 系统调用保存操作，**Then** 偏移量 1024 被写入持久化文件
2. **Given** 持久化文件中记录了多个输入源的状态，**When** 系统重新加载状态，**Then** 每个输入源恢复到各自保存时的偏移量
3. **Given** 持久化文件不存在（首次运行），**When** 系统加载状态，**Then** 所有输入源从零偏移量开始，不报错
4. **Given** 去重存储中不存在某个快照键，**When** 检查该键是否需要处理，**Then** 返回"需要处理"
5. **Given** 一个快照处理完成，**When** 标记为"已处理"状态，**Then** 更新高水位线为该快照的时间戳（如果更大）
6. **Given** 去重存储中存在发现时间超过保留期的条目，**When** 系统执行清理操作，**Then** 这些过期条目被删除

---

### 用户故事 3 — 异构数据归一化与序列化（Normalization）（优先级：P1）

作为平台开发者，我需要一个统一的归一化层，将来自不同 AI Agent 的异构原始数据转换为标准的 `AgentActivityEntry` 格式，并提供序列化和脱敏能力，确保下游输出模块只需处理一种数据结构。

**优先级理由**: 归一化是连接上游采集和下游输出的核心桥梁，避免 O(M×N) 的组合爆炸。

**独立测试**: 可通过传入不同 Agent 类型和操作类型的参数调用工厂方法，验证产出的记录包含所有必需字段、UUID 唯一、时间戳格式正确。

**验收场景**:

1. **Given** 提供了会话 ID、Agent 类型、操作类型等必需参数，**When** 调用归一化工厂方法，**Then** 返回包含唯一 UUID 和毫秒级时间戳的标准活动记录
2. **Given** 一个包含基础字段的活动记录，**When** 执行序列化，**Then** 输出的扁平对象包含 `sessionId`、`timestamp`、`uuid` 等字符串键值对，Git 嵌套结构被展平
3. **Given** 扩展字段中包含预定义的敏感/冗余键，**When** 执行序列化，**Then** 这些键被自动过滤不输出
4. **Given** 一个包含代码内容的序列化记录，**When** 执行脱敏操作，**Then** `filePath`、`content`、`inlineDiffMessage` 被移除，原始对象未被修改

---

### 用户故事 4 — 可靠的多目标数据输出（Flushers）（优先级：P1）

作为平台运维人员，我需要系统能够将归一化后的活动记录同时输出到多个目标（本地 JSONL 文件、阿里云 SLS、HTTP 服务），确保单个通道失败不影响其他通道。

**优先级理由**: 数据输出是采集平台交付价值的最终环节。

**独立测试**: 可通过同时启用 JSONL 和 HTTP 两个输出通道，模拟 HTTP 通道失败，验证 JSONL 通道仍然正常写入。

**验收场景**:

1. **Given** 系统配置了 SLS、JSONL、HTTP 三个输出通道，**When** 输入源产出一批活动记录，**Then** 三个通道同时接收到相同的数据，互不阻塞
2. **Given** 其中一个输出通道发生网络错误，**When** 数据批次被发送，**Then** 失败通道记录错误日志，其余通道正常完成输出
3. **Given** 没有任何输出通道被显式启用，**When** 系统启动，**Then** 系统自动使用 JSONL 作为兜底输出通道
4. **Given** JSONL 启用了每日轮转，**When** 系统在不同日期写入数据，**Then** 数据被写入以 `{agentType}-{YYYY-MM-DD}.jsonl` 命名的不同文件
5. **Given** SLS 上报因网络问题失败，**When** 批次发送异常，**Then** 失败的批次被持久化到本地文件，不丢失数据
6. **Given** 系统正在优雅关闭，**When** 缓冲区中还有未发送的数据，**Then** 系统在关闭前执行最后一次刷写

---

### 用户故事 5 — 一键启动与优雅关闭（Core 编排）（优先级：P1）

作为平台运维人员，我需要通过一条启动命令让系统自动完成配置加载、状态恢复、输出通道初始化、输入源注册和 Agent 发现，并在收到终止信号后有序关闭所有子系统。

**优先级理由**: 编排启动是整个系统运行的前提。

**独立测试**: 可通过在测试环境中构造最小配置，验证启动后系统进入运行状态且各子系统正常工作。

**验收场景**:

1. **Given** 提供了有效的配置，**When** 启动编排器，**Then** 系统按顺序完成：数据目录初始化 → 状态存储加载 → Agent 控制加载 → 输出通道构建 → 输入源注册 → Agent 发现启动
2. **Given** 系统正在运行，**When** 收到 SIGINT 或 SIGTERM 信号，**Then** 系统按顺序执行：停止发现 → 停止输入源 → 刷写输出通道 → 保存状态 → 进程退出
3. **Given** 关闭过程中某个子系统停止失败，**When** 系统继续关闭流程，**Then** 错误被记录但不阻塞其他子系统的关闭

---

### 用户故事 6 — 自动发现与准入控制（Core 编排）（优先级：P2）

作为平台运维人员，我需要系统自动检测宿主机上已安装的 AI Agent 并管理其生命周期，同时支持通过配置文件控制采集开关。

**优先级理由**: 自动发现是无人值守运行的核心能力。

**独立测试**: 可通过模拟一个 Agent 的数据目录从不存在到创建的过程，验证发现服务检测到变化后自动启动对应输入源。

**验收场景**:

1. **Given** 系统启动时某个 Agent 的数据目录已存在，**When** 发现服务执行首次检查，**Then** 该 Agent 的输入源被自动启动
2. **Given** Agent 控制配置中某个 Agent 设为"强制关闭"，**When** 发现服务评估该 Agent，**Then** 该 Agent 被视为"已禁用"，即使其数据目录存在
3. **Given** 配置文件支持环境变量 > 配置文件 > 内置默认值三层合并，**When** 同时设置环境变量和配置文件中的同一字段，**Then** 环境变量的值优先生效

---

### 边界用例

- 数据文件为空或仅包含空行时，输入源应返回空结果集且不报错
- 数据文件包含畸形 JSON 行时，应跳过该行并记录警告，继续处理后续行
- SQLite 数据库文件被其他进程锁定时，应记录警告并等待下一轮询周期重试
- 持久化文件内容为空或无效 JSON 时，系统应重置为空状态而非崩溃
- 活动记录列表为空时，输出通道应正常完成而不产生任何副作用
- JSONL 输出目录不存在时，系统应自动创建目录
- 多个输出通道同时刷写时，彼此之间不应存在资源竞争
- 所有输出通道配置都被禁用时，系统应自动使用 JSONL 兜底输出
- Agent 控制文件格式损坏时，系统应使用默认的"全部自动"模式
- 时间戳以秒为单位时，序列化方法应自动转换为毫秒

## 需求 *(必填)*

### 功能需求

**输入源框架**

- **FR-001**: 系统必须支持 5 种采集方式：IDE 历史快照轮询、SQLite 增量轮询、Hook JSONL 日志采集、CLI 遥测日志转发、会话文件轮询
- **FR-002**: 每种采集方式必须有对应的抽象基类，封装通用的轮询循环、状态管理和事件发射逻辑
- **FR-003**: 所有输入源必须将采集到的原始数据归一化为统一的 `AgentActivityEntry` 格式
- **FR-004**: 输入源必须实现优雅的生命周期管理（`start`/`stop`），确保停止时正确释放资源并持久化状态
- **FR-005**: 新增 Agent 输入源时，必须仅需继承基类、实现抽象方法并在编排器中注册，不得修改现有代码

**持久化层**

- **FR-006**: 系统必须提供 `StateStore`，支持按输入源 ID 读写多维度采集进度（偏移量、rowid、时间戳、扩展字段）
- **FR-007**: `StateStore` 必须实现脏标记机制——仅在状态有实际变更时执行文件写入
- **FR-008**: 系统必须提供 `SnapshotStore`，支持基于唯一键的 IDE 事件去重，实现"待处理/已处理"两阶段状态机
- **FR-009**: `SnapshotStore` 必须支持基于发现时间的自动过期清理和高水位线驱动的扫描范围缩小
- **FR-010**: 两种存储的持久化文件在缺失或损坏时，必须优雅降级为空状态

**归一化层**

- **FR-011**: 系统必须提供统一的工厂方法（`buildAgentActivityEntry`），为每条记录生成全局唯一 UUID 和毫秒级时间戳
- **FR-012**: 系统必须提供序列化方法，将活动记录转换为扁平字符串键值对，Git 嵌套结构展平为顶层键
- **FR-013**: 序列化方法必须自动过滤扩展字段中的预定义敏感/冗余键，自动检测并修正秒级时间戳
- **FR-014**: 系统必须提供独立的脱敏方法，从序列化记录中移除代码相关字段，返回新对象不修改原始输入

**数据输出**

- **FR-015**: 系统必须支持 3 种输出通道：JSONL 本地文件、阿里云 SLS、HTTP POST
- **FR-016**: 系统必须提供 `MultiFlusher` 多目标扇出能力，单个通道故障必须被隔离
- **FR-017**: JSONL 输出通道必须支持按日期轮转文件和 `sendRaw` 原始数据写入
- **FR-018**: SLS 输出通道必须支持多 Endpoint 路由、敏感字段脱敏和批量发送
- **FR-019**: SLS 和 HTTP 发送失败时必须有容错机制（SLS 持久化到本地文件，HTTP 放回缓冲区重试）
- **FR-020**: 所有输出通道必须支持优雅关闭——在关闭前刷写所有缓冲数据

**核心编排**

- **FR-021**: 系统必须提供中枢编排器，按确定顺序初始化和串联所有子系统，启动和停止操作幂等
- **FR-022**: 系统必须提供 Agent 发现服务，支持文件系统监听和定时轮询两种模式（监听不可用时自动降级）
- **FR-023**: 系统必须提供三级准入控制（强制开启/强制关闭/自动检测），通过独立配置文件管理
- **FR-024**: 系统必须提供配置加载器，按"环境变量 > 配置文件 > 内置默认值"的优先级合并配置
- **FR-025**: 系统必须响应 SIGINT/SIGTERM，按确定顺序关闭所有子系统，单个失败不阻塞其他

### 关键实体

- **BaseInput（输入基类）**: 封装轮询循环、事件发射和状态管理的抽象基类，具有 `start`/`stop` 生命周期和 `collect()` 抽象方法
- **StateStore（状态存储）**: 管理所有输入源采集进度的集中式 JSON 文件存储
- **SnapshotStore（快照去重存储）**: 管理 IDE 快照事件的去重、过期清理和高水位线
- **AgentActivityEntry（活动记录）**: 归一化后的标准数据格式，是所有输入源的统一输出
- **SerializedLogEntry（序列化记录）**: 活动记录经过序列化后的扁平键值对，是所有输出通道的统一传输格式
- **BaseFlusher（输出基类）**: 定义统一的输出接口（`send`/`sendBatch`/`flush`/`shutdown`/`sendRaw`）
- **MultiFlusher（多目标扇出器）**: 将数据并行分发到多个输出通道，隔离单个通道的失败
- **Orchestrator（编排器）**: 系统中枢控制器，负责初始化所有子系统、管理生命周期、串联数据流
- **AgentDiscoveryService（发现服务）**: 检测宿主机上 AI Agent 的安装状态，驱动输入源的自动启停
- **InputManager（输入管理器）**: 统一注册和管理所有输入源，订阅事件并分发到输出通道
- **ConfigLoader（配置加载器）**: 三层配置合并（环境变量 > 文件 > 默认值）

## 成功标准 *(必填)*

### 可衡量的结果

- **SC-001**: 增量采集的准确率达到 100%——不丢失、不重复处理任何数据记录
- **SC-002**: 进程重启后，所有输入源在 5 秒内从持久化状态恢复并开始采集，无数据丢失
- **SC-003**: 新增一个基于现有采集方式的 Agent 输入源，开发者仅需编写不超过 200 行代码
- **SC-004**: 在多通道同时启用的情况下，单个通道故障不导致其他通道数据丢失，故障隔离成功率 100%
- **SC-005**: 优雅关闭从收到信号到进程退出的总时间不超过 15 秒
- **SC-006**: 所有输入源（当前 4 种 Agent）通过归一化工厂方法产出的活动记录格式一致率 100%
- **SC-007**: 序列化输出可被所有 3 种输出通道直接使用，无需额外转换
- **SC-008**: SLS 发送失败时，100% 的失败批次被持久化到本地文件
- **SC-009**: 配置合并的正确性达到 100%——环境变量始终优先于配置文件、配置文件始终优先于默认值
- **SC-010**: 系统从启动到首次 Agent 发现完成的时间不超过 5 秒

## 假设

- 宿主机上的 AI Agent 数据目录对当前进程可读
- 各 Agent 的数据文件格式在同一大版本内保持稳定
- 系统运行在 Node.js 18+ 环境中，可使用 `fs.watch`、`better-sqlite3` 等原生模块
- 系统以单进程模式运行，编排器实例全局唯一
- SLS SDK（`@alicloud/log`）可用且网络可达阿里云服务端点
- 同一时刻每个输入源仅有一个轮询周期在执行，不存在并发轮询
- 状态存储实例在单进程内使用，不存在多进程并发读写
