# Codex 超大 JSONL 记录性能修复与压测报告

测试日期：2026-10-30。对照基线为 `main` 提交 `f84e3881`，修复版本为 `bb326bf1`。本报告只包含隔离测试的汇总数据，不包含客户日志、用户标识、本地路径、接入地址或凭据。

## 问题与修改

普通会话扫描在 16 MiB 预算内找不到换行时，会回退到从行首读取完整记录。原扫描器逐块拼接、复制并搜索不断增长的缓冲区，处理成本近似 O(n²)。完整巨行还可能在 `JSON.parse` 的异常保护之前执行 `Buffer.toString()` 时超过 Node 字符串长度上限，导致采集轮次失败、checkpoint 不推进，下轮再次读取同一范围。

本次修改公共 JSONL 扫描器：

- 保存分块引用，每条完整记录最多拼接一次，避免逐块复制和搜索整个累积前缀。
- 限制单行内容为 128 MiB（不含 LF）；超限后释放已保存的分块，只继续查找换行，不再解码或解析该记录。
- 遇到 LF 后才明确跳过超限完整记录，计入解析失败并输出 `record-too-large` 诊断，允许后续记录推进；未换行尾部不提交。
- 诊断包含路径哈希、偏移、记录长度和限制值，不包含正文或完整路径。源 transcript 保持完整。
- 将 Buffer 转字符串纳入解析异常保护。

超过 128 MiB 的有效业务记录同样会被跳过常规采集。原始内容仍在源文件中，但本变更不提供独立隔离副本或自动重放机制，不保证任意大小记录无损采集。128 MiB 也不是整个 collector 的 RSS 上限。

## 测量方法

- macOS arm64，同一台 48 GiB 内存主机；两版分别从 Git 快照构建，复用相同依赖。
- 主对照使用 Node 22.22.2、默认 JS 堆配置、1 秒输入轮询；真实会话由 Codex CLI 0.147.0 调用百炼 `qwen3.8-max` 生成。
- collector 使用隔离的 HOME、CODEX_HOME、数据目录、配置和端口。先启动空会话目录，等待原生 orchestrator 就绪，再发布测试输入，避免启动基线跳过数据。
- 每个性能场景两版处理逐字节相同的输入。真实会话先生成一次，再由两版独立重放，避免不同模型执行结果干扰对照。
- 每秒采样 collector 子进程的 `process.cpuUsage()` 和 `process.memoryUsage()`，不计模型生成进程的 CPU。100% CPU 约为一个核，可以超过 100%。
- 对会话文件的 FileHandle.read 记录实际返回字节与调用次数；逻辑读取量包含辅助恢复回读，不等于物理磁盘 I/O。
- 按 main → 修复版顺序单次执行；每版采样约 45–90 秒。启动和停止排空另计；1 秒采样可能遗漏更短峰值。
- 两版使用相同遥测输出配置。性能结论和事件对照以各自独立的本地测量与输出为准。

## 完整巨行故障注入

普通会话中注入一条携带 544 MiB ASCII 内容的完整 `FileChange` 记录，前后包含合法输入、模型响应、Token 和终态。文件总长 570,426,576 字节，巨行超过 Node 字符串上限及本补丁的单行上限。该输入不来自客户或真实模型执行。

| 指标 | main | 修复版 |
| --- | ---: | ---: |
| 采样区间 | 90.184 s | 90.028 s |
| 平均 CPU | **96.97%** | **3.37%** |
| CPU p95 / 峰值 | 125.76% / 178.43% | 3.58% / 38.60% |
| RSS 峰值 | **10,224.33 MiB** | **325.23 MiB** |
| 字符串长度异常 | 1 | 0 |
| 输出事件 | 0 | 5 |
| checkpoint | 608，停在巨行起点 | 570,426,576，即 EOF |
| active / pending | active 保留 | 全部清除 |
| 退出 | SIGTERM 后 30 秒未排空，最终 SIGKILL | 正常退出 0 |

main 实际出现 `Cannot create a string longer than 0x1fffffe8 characters`，随后从相同断点继续读取。修复版跳过完整超限记录，处理后续终态并恢复空闲。

该故障窗口平均 CPU 降低约 96.5%，采样 RSS 峰值降低约 96.8%。main 没有完成工作，修复版完成了策略允许的后续采集，因此不能将这些比例表述为相同成功吞吐下的通用性能提升。

采样段 main 逻辑读取约 1.03 GB，含停止排空阶段约 1.18 GB；修复版一次性扫描及必要恢复共读取约 1.75 GB，之后不再增长。**本次短窗口修复版总读取量并不小于 main，不能声称全窗口读取下降。** 修复版最后约 30 秒读取增量为 0，平均 CPU 约 2.81%。

修复版在普通扫描和 turn 恢复中共记录 3 次超限诊断，仍有有限回读；这不是完全单次读取。超限正文没有进入常规输出，源文件保留，不能把处理后续终态解释为超限内容无损采集。

另两轮 Node 24 预试跑（默认堆及 512 MiB JS 堆）均在字符串转换之前触发 8 GiB RSS 保护，停止阶段采样峰值超过 10 GiB。它们未完成相同工作，不参与主表的百分比计算，也说明仅限制 JS 堆不能解决外部 Buffer 膨胀。

## 未换行尾部边界对照

在普通会话尾部写入约 32 MiB 的 JSON 内容但不写 LF，两版读取同一个静止文件，观察约 45 秒，可计算采样区间约 44 秒。

| 指标 | main | 修复版 |
| --- | ---: | ---: |
| 平均 CPU | 27.09% | 5.71% |
| CPU p95 / 峰值 | 32.35% / 33.98% | 7.40% / 9.86% |
| RSS 峰值 | 1,254.45 MiB | 228.52 MiB |
| 采样段逻辑读取 | 2,183,207,438 B（约 2.03 GiB） | 相同 |
| 全过程读取字节 / 次数 | 2,233,539,230 / 2,176 | 相同 |
| 输出事件 | 0 | 0 |
| 退出状态 | 0 | 0 |

未遇到 LF 时不提交该行、没有终态输出是预期行为。平均 CPU 降低约 78.9%、RSS 峰值降低约 81.8%，但**静止尾部仍被反复读取，读取量逐字节相同**。本补丁降低了复制成本，没有解决这条路径的跨轮 I/O 放大；仍需保存物理扫描进度及文件变化状态。

## 边界和范围

- 初次试跑有多个 collector 使用相同 trace/span 身份重复投递到同一应用，云端调用树、Token 汇总和时长受污染，不作为本报告依据。压测脚本随后增加了每 run、每 variant 的独立会话身份；后续可视化回放与原始同字节性能比较分开记录。
- 本地事件等价不等同于完整的云端 trace 拓扑验收。重复接入和 ENTRY 展示问题本轮不修改，不包含在性能修复的验收结论中。
- 本次没有覆盖三个连续十分钟窗口，不能外推为长期持续高 CPU 人群改善或线上 CPU 降幅；也没有测得可推广的稳定吞吐提升。
- 后续仍需治理未换行尾部续扫、fork 起点搜索、缺元数据探测及 pending/context 恢复预算。
