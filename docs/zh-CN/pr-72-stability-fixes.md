# PR #72 稳定性修复说明

## 一句话总结

这次修复主要解决了三个问题：**队列超限时可能仍然占用过多内存、日志积压时 CPU 开销过大、程序重启时可能重复发送或反复读取坏文件**。

同时，我们也把 PR 与最新 `main` 的冲突解决了，保留了两边已有的稳定性能力。

## 整体流程

```text
新日志
  │
  ▼
内存队列 ── 正常发送 ──▶ SLS
  │
  ├─ 临时发送失败 ──▶ 等待后重试
  │
  ├─ 队列超过上限 ──▶ 淘汰全局最旧日志
  │                     └─ 记录失败元数据
  │
  └─ 程序关闭仍未发完 ──▶ 保存 pending 文件
                            └─ 下次启动安全恢复
```

## 1. 队列超限时，真正限制住内存

### 原来的问题

日志按不同 Agent、不同目标分在多个队列中。

以前发现“总队列超限”后，只会清理当前正在写入的那个队列，而且优先丢弃刚产生的最新日志。可能出现：

- 当前队列已经清空，但其他队列仍然很大；
- 总队列仍超过限制，内存没有真正降下来；
- 最新日志被丢弃，较旧日志反而继续占用空间。

### 现在的处理

从所有队列中找出**全局最旧的日志**，按先进先出（FIFO）的顺序淘汰，直到总量回到限制以内。

效果是：

- 队列条数和内存大小上限真正生效；
- 优先保留较新的日志；
- 某一个 Agent 停止产生新日志，也不会让它的旧队列一直占着内存。

## 2. 日志积压时，降低 CPU 开销

### 原来的问题

每进入一条新日志，程序都会多次遍历整个队列，重新计算日志条数和大小。

平时队列很短，影响不明显；但 SLS 故障、积压上万条日志时，每条新日志都要扫描大量旧日志，容易形成：

```text
SLS 故障
  ▼
队列越来越大
  ▼
每次计算越来越慢
  ▼
CPU 开销继续升高
```

### 现在的处理

改为维护实时计数：

- 入队时增加条数和字节数；
- 发送、淘汰或过期时扣减；
- 查询队列状态时直接读取计数，不再遍历全部日志。

这样即使队列很大，单次状态计算也基本保持固定成本，避免故障期间 CPU 压力被二次放大。

## 3. 重启恢复更加安全

### 原来的问题

程序关闭时，如果还有日志没发完，会写入 pending 文件，下次启动再恢复。

以前的顺序是：

```text
读取文件 → 重新入队/发送 → 删除文件
```

这里存在两个风险：

1. 日志发送后、文件删除前进程崩溃，下次启动会再次发送，产生重复数据；
2. 文件中只要有一行损坏，每次启动都会再次读取并失败，形成死循环。

### 现在的处理

```text
先完整校验
  │
  ├─ 文件损坏 ──▶ 移到 .corrupt
  │
  └─ 文件正常
       ▼
     原子改名为 .restoring
       ▼
     重新入队
       │
       ├─ 成功 ──▶ 删除文件
       └─ 失败 ──▶ 移到 .failed
```

文件在恢复前就会被“认领”，即使恢复过程中进程崩溃，也不会在下次启动时自动重复发送。

这里采用的是**最多发送一次（at-most-once）**策略：优先避免重复数据。异常文件仍然保留，可以人工检查或恢复。

## 4. 与最新 main 的冲突处理

最新 `main` 引入了统一的失败日志写入组件，只保存有界、脱敏的失败元数据，避免失败日志本身无限占用磁盘。

合并时保留了：

- PR 的重试、背压、队列上限和 pending 恢复；
- `main` 的统一失败日志管理；
- `main` 的 endpoint 独立服务名能力；
- 两边新增的指标和测试。

发送失败仍由外层统一判断：

- 临时故障：保留在队列中重试；
- 永久故障、重试过期或队列超限：记录失败元数据并移出队列。
