# LoongSuite Pilot 项目宪法

## 核心原则

### I. 代码质量

所有生产代码必须遵循严格的质量标准，以维持长期可维护性并降低
代码库的缺陷率。

- 每个模块必须具有单一且明确定义的职责。输入源（inputs）、
  输出器（flushers）、归一化器（normalizers）和核心编排层必须
  保持在各自的分层中，禁止跨层耦合。
- 所有公开 API 必须使用 TypeScript strict 模式并提供显式类型
  标注。禁止使用 `any`；当外部数据进入系统时，应使用 `unknown`
  配合 Zod schema 进行运行时校验。
- 资源管理必须规范化：所有 I/O 句柄（SQLite 连接、文件描述符、
  HTTP 客户端）必须通过确定性的生命周期方法（`start`/`stop`）
  进行获取和释放。
- 函数逻辑行数必须控制在 50 行以内（不含类型定义和 import）。
  复杂度增长时必须提取辅助函数。
- 合并前必须清除死代码、未使用的 import 和注释掉的代码块。
  Lint 检查（`tsc --noEmit`）必须零错误通过。
- 命名必须具有描述性且保持一致：变量和函数使用 `camelCase`，
  类和类型使用 `PascalCase`，常量使用 `SCREAMING_SNAKE_CASE`。
  类的成员变量必须使用下划线前缀或 `m_` 前缀。

### II. 测试规范

每个行为变更必须伴随相应的测试来验证正确性并防止回归。

- 单元测试必须覆盖输入源、输出器、归一化器和工具模块的所有
  公开方法。新代码的最低覆盖率目标：80% 行覆盖率。
- 集成测试必须验证每种采集方式的端到端数据流：IDE 快照轮询、
  SQLite 增量读取、Hook JSONL 采集、CLI 遥测转发和会话文件
  轮询。
- 契约测试必须验证归一化后的 `AgentActivityEntry` 输出符合
  声明的 Zod schema，与输入源无关。
- 边界用例必须被显式测试：空输入、畸形 JSON、文件缺失、权限
  错误、SQLite 锁争用和网络超时。
- 测试必须是确定性的。文件系统、网络和时间依赖必须使用 stub
  或 mock。禁止在 CI 中依赖真实外部服务的测试。
- 测试名称必须用清晰的自然语言描述场景和预期结果（例如：
  `"当会话文件为空时返回 null"`）。

### III. 用户体验一致性

所有数据采集、配置和运维接口必须为操作人员和集成方提供一致、
可预期的体验。

- 配置必须遵循严格的优先级链：环境变量 > 配置文件 > 内置默认值。
  此顺序在所有模块中不得改变。
- 所有面向用户的错误消息必须包含：（1）发生了什么错误，
  （2）可能的原因，（3）建议的修复操作。禁止向操作人员暴露
  晦涩的错误信息或原始堆栈跟踪。
- 日志输出必须使用结构化 JSON 格式，并在所有模块中使用一致的
  字段名（`timestamp`、`level`、`component`、`message`、
  `details`）。日志级别（`debug`、`info`、`warn`、`error`）
  必须一致使用：`error` 用于需要操作人员介入的故障，`warn` 用于
  降级但可恢复的状态，`info` 用于生命周期事件，`debug` 用于
  诊断详情。
- CLI 输出和退出码必须遵循 Unix 惯例：成功 exit 0，失败非零。
  人类可读输出到 stdout，错误输出到 stderr。
- 新增 Agent 输入源时不得要求修改现有的输入源或输出通道。
  插件架构（继承基类、在编排器中注册）必须是唯一的集成路径。

### IV. 性能要求

系统必须在定义的资源边界内高效运行，确保持续数据采集的可靠性，
且不对宿主机造成影响。

- 稳态内存使用量必须低于 150 MB RSS。内存增长必须有上界：
  快照存储必须自动过期超过配置保留期（默认 7 天）的条目。
- 轮询间隔必须支持按输入源单独配置。默认间隔不得超过：
  IDE/SQLite 源 60 秒，会话文件源 30 秒。为防止过度 I/O，
  禁止设置低于 5 秒的间隔。
- 批量刷写必须是所有输出通道的默认行为。SLS 和 HTTP 输出器
  必须至少累积 20 条记录或每 2–5 秒刷写一次（以先到者为准）。
  除优雅关闭的排空阶段外，禁止单条记录刷写。
- 文件 I/O 必须使用增量读取（基于偏移量/游标），禁止全文件
  重新读取。SQLite 查询必须使用带索引的 `rowid` 游标。
  超过 10,000 行的表禁止全表扫描。
- 优雅关闭必须在 10 秒内完成：所有待处理批次必须刷写完毕，
  所有文件句柄和数据库连接必须关闭，状态必须在进程退出前
  持久化。
- CPU 密集型操作（大型载荷的 JSON 解析、内容脱敏）不得阻塞
  事件循环超过 50ms。对于大数据集须使用分片处理或
  `setImmediate` 让出控制权。

## 开发工作流

所有贡献者必须遵循一致的开发工作流，以确保代码质量和项目稳定性。

- 所有变更必须通过功能分支提交。禁止直接向主分支提交代码。
- 每个 Pull Request 在合并前必须通过类型检查（`tsc --noEmit`）、
  所有现有测试和 Lint 检查。
- 代码审查必须验证是否遵循全部四项核心原则。审查者必须显式
  检查：类型安全、新行为的测试覆盖、一致的错误处理，以及新增
  轮询或 I/O 操作的性能影响。
- 提交信息必须遵循约定式提交格式（`type: description`），其中
  type 为以下之一：`feat`、`fix`、`refactor`、`test`、`docs`、
  `chore`、`perf`。
- 添加依赖必须保持克制。每个新增依赖必须附带合理性说明。优先
  使用标准库和现有依赖，而非引入新包。

## 质量门禁

所有代码在被视为生产就绪之前必须通过以下门禁。

- **类型安全门禁**：`tsc --noEmit` 必须零错误零警告通过。
  strict 模式必须保持开启。
- **测试门禁**：所有单元测试和集成测试必须通过。新代码必须
  包含测试；将整体覆盖率降至 80% 以下的 PR 必须拒绝。
- **Schema 校验门禁**：所有 `AgentActivityEntry` 输出必须通过
  Zod schema 校验。Schema 变更必须向后兼容或显式版本化。
- **性能门禁**：新增输入源或输出器必须提供基准测试证据，
  证明满足原则四中定义的轮询间隔和内存约束。
- **运维就绪门禁**：新功能必须包含适当级别的结构化日志、
  优雅的错误恢复机制和配置文档。

## 治理

本宪法是项目标准的权威来源。所有开发决策、代码审查和架构选择
必须遵守本文定义的原则。

- **修订流程**：对本宪法的任何修改必须以 Pull Request 形式
  提出，并附带明确的修改理由。核心原则的变更需要团队明确审查
  和批准。
- **版本策略**：本宪法遵循语义化版本。移除原则或不兼容的
  重新定义触发 MAJOR 升级，新增原则或实质性扩展触发 MINOR
  升级，澄清和措辞修正触发 PATCH 升级。
- **合规审查**：每次代码审查必须包含宪法合规检查。违规项必须
  在合并前解决，除非在 PR 描述中明确说明理由并记录。
- **冲突解决**：当本宪法与外部指南或工具默认值冲突时，在项目
  范围内以本宪法为准。
