# Issue 正文格式

Issue 发布到 [Code 平台](https://code.alibaba-inc.com/sls/loongsuite-pilot/issues)，类型为 `BUG`，描述格式为 `MARKDOWN`。

## 标签约定

每个 Issue 创建后必须打齐以下标签：

| 标签 | 示例 | 用途 |
|------|------|------|
| `pilot-alarm` | `pilot-alarm` | 标识来源，用于筛选本 skill 创建的 Issue |
| `<ALARM_TYPE>` | `UPDATER_FAILURE_ALARM` | 告警类型，用于去重 |
| `<P0\|P1\|P2\|P3>` | `P0` | 优先级 |

## 去重规则

去重维度：**同 `alarm_type` + 未关闭**。

通过 `list_issues`（status=new,assigned）获取列表，检查标题是否包含对应告警中文名，或通过 `get_issue` 检查标签是否含 `<ALARM_TYPE>`。

- 找到未关闭同类 → 追加评论（写增量变化，不重贴全文）
- 未找到 → 新建
- 已关闭同类 → 可新建

---

## 正文写作要求

Issue 面向的读者是**不了解分析过程的开发者**。写完后自查：一个没参与分析的同事是否能看懂、能复现验证、能拿着修复建议直接开工。

### 写作红线（违反则不合格）

| 禁止 | 应该 |
|------|------|
| 缩写、黑话（pidmm、cmdmm、SNR、UNR） | 用完整中文或全称（pid 不一致、服务未运行告警） |
| 只贴数字无上下文（`stale 806 > pidmm 495`） | 用完整句子解释数字含义（「心跳过期」模式影响 806 个 Agent，是最主要的触发原因） |
| Verification 只写结论不记过程 | 每条验证写清：**验证目的 → 查询命令 → 返回结果 → 结论**，让人能复现 |
| Root Cause 用代码术语堆砌 | 用「现象→机制→为什么」的逻辑链解释，代码路径作为引用而非主线 |
| 修复建议太抽象（「加 grace」） | 写清改哪个文件、哪个函数、怎么改、预期效果 |

## 正文模板

以下为 Issue 描述（description）的 Markdown 模板：

````markdown
## 问题概述

用 2-3 段**自然语言**描述：
- 什么问题（告警类型、严重级别、从什么时候开始或是否持续存在）
- 影响了谁、影响多大（Agent 数、用户数、占舰队总量的比例）
- 核心表现是什么（最典型的告警消息是什么、用户会感知到什么）

## 优先级

| 维度 | 评级 | 说明 |
|------|------|------|
| 影响范围 | XL / L / M / S | 对照 Agent 数与用户数解释 |
| 严重程度 | Critical / High / Medium / Low | 对功能的实际影响 |
| 修复难度 | Easy / Medium / Hard | 预估修改范围与风险 |
| **综合** | **P0 / P1 / P2 / P3** | 一句话总结 |

## 影响面分析

用完整段落或表格展示：
- 影响最大的用户（Top 5，含各用户名下的 Agent 数与告警类型组合）
- 版本分布（哪些版本受影响，是否集中在某一版本）
- 与其他告警的关联（是否独立问题，还是某个更大问题的衍生症状）

## 告警消息分类

将窗口内所有告警消息按**模板**归类（将数字、IP、路径等替换为占位符后归并），用表格列出：

| 消息模板 | 影响 Agent 数 | 含义说明 |
|----------|-------------:|----------|
| `updater heartbeat is stale` | 806 | Updater 进程的心跳文件超过 3 分钟未更新 |
| ... | ... | ... |

## 代码分析

用**自然语言段落**讲清楚代码逻辑，不要只列文件名：
- 告警在什么模块、什么函数中被触发
- 触发条件是什么（用 if/when 的语言描述业务逻辑，而非贴代码片段）
- 从触发到告警发出经过了哪些中间步骤
- 如果有多个代码路径能触发同一告警，逐一说明并标注各自的影响占比

引用代码位置时用 `文件路径:函数名` 格式，例如 `src/core/updater-watchdog.ts:runCheck`。

## 验证过程

**每条验证**按以下结构书写：

### 验证 N：<验证目的的一句话描述>

**目的**：我们想确认 XXX 是否成立。

**方法**：通过查询 SLS 的 `loongsuite_alarm` / `loongsuite_status` 日志，统计 YYY。

**查询命令**：

```bash
python3 .agents/skills/alarm-triage/scripts/query_sls.py --logstore alarm --pretty --query "
<完整的 SQL 查询>
"
```

**结果**：

| 字段 | 值 |
|------|---|
| ... | ... |

**结论**：XXX 假设成立 / 不成立，因为 ZZZ。

---

原始查询结果 JSON 存放在：`data/runs/<day>/analysis/<ALARM_TYPE>.json`

## 根因

用 1-3 段自然语言描述：
1. **主要原因**：完整描述因果链（什么条件 → 触发什么逻辑 → 导致什么结果），引用验证中的具体数据支撑
2. **次要原因**（如有）：同上格式
3. **已排除的假设**：简要列出曾考虑但已通过验证排除的假设及排除理由

## 修复建议

每条建议按以下格式：

### 建议 N：<一句话概括>

- **要改什么**：涉及的文件和函数
- **怎么改**：具体的修改思路（不需要写代码，但要足够清晰到开发者能直接动手）
- **预期效果**：修复后预计消除多少 Agent 的告警、解决什么问题
- **风险与注意**：可能的副作用或需要额外验证的点

## 待确认项

仅限**无法通过 SLS 查询或读代码来验证**的项目（例如需要登录用户机器查看本地文件）。
每条写清：需要确认什么、为什么远程无法确认、确认后可能改变什么结论。

可以为空（没有待确认项时写「无」）。
````
